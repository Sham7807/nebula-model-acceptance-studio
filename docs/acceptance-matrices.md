# 参数矩阵与报告判读

工作台通过多场景、多参数和对照请求检查当前渠道的可观察行为。一次测试的结论仅适用于报告记录的模型、协议、参数和负载，不能代替官方来源认证或长期容量测试。

## 开始一次完整验收

1. 填写渠道、密钥并选择模型和实际请求格式。模型名称不会自动决定协议。
2. 通用检测选择「标准」或「完整」；CCMax、Claude、KVV 选择对应的「参数矩阵与阶梯压测」方案。
3. 勾选本轮范围。服务端的原专项模块与追加矩阵分别控制；选择「仅运行原专项」时不执行追加矩阵。
4. 预览请求与用量，再开始。预览不调用模型、不传 API Key；批量会对每个模型独立执行，实际用量累加。
5. 在统一 HTML 报告先看结论、可判定率和失败原因，再查看维度、参数表与请求证据。

## 每个层面如何取证

| 层面 | 参数和对照 | 结论依据 |
| --- | --- | --- |
| 输出上限 | 快速 1/10/20；标准双场景和流式/非流式；完整另加 64/128/256、三场景和重复采样 | 原始输出 Token 计数、结束原因、合法响应结构；缺 usage 明确为证据不足 |
| 工具 | 强制、指定、禁用、自动选择，嵌套对象、数组、枚举、多工具与回填 | 名称、关联 ID、JSON 参数、Schema 约束、回填结果；自然语言答案不能代替工具调用 |
| 多模态 | 已知颜色图、计数图、多图顺序与关联，通用格式支持的其他模态 | 实际发送的图片、已知答案、每项独立断言；图片通过不代表视频或音频通过 |
| 注入与指令 | 本轮合成标记、系统层约束、直接/文档/工具数据等变体 | 标记是否泄露或覆盖、前置正对照和可见输出；不读取真实业务秘密 |
| 缓存 | 本轮唯一长前缀、完全重复、后缀变化、前缀首部变化 | 实际输入规模、原生缓存读写 usage 和对照变化；耗时降低本身不算命中 |
| 协议与透传 | 流式/非流式、Unicode、结构化文本、停止词、非法参数 | 原始请求、合法响应、结束帧、usage；完全透传仍需上游日志逐字段核对 |
| 压测 | 先低并发，再按阶段升高；固定请求数、超时与取消 | HTTP 分布、请求完成率、内容匹配率、P50/P95、首字节时间；不自动重试抹掉失败 |

输出预算包括模型可能使用的思考 Token。`max_tokens=1` 返回空正文但报告 1 个输出 Token 与截断结束，可以通过上限检查；需要正文的工具/指令等检查如果预算耗尽，应补充语义证据，不能直接判为成功或模型失效。

## 服务端追加矩阵的规模

以下数量仅计算追加矩阵，全选模块、每个模型一次；原专项请求另计。具体请求体以当前部署版本的预览为准。

| 方案 | 截断变体 | 较大预算长输出对照 | 阶梯负载：并发 × 请求数 | 矩阵请求上限 |
| --- | ---: | ---: | --- | ---: |
| 快速 | 3 | 1 | 1×2 → 2×4 | 27 |
| 标准 | 12 | 2 | 1×4 → 2×4 → 4×8 | 59 |
| 完整 | 72 | 3 | 1×8 → 2×8 → 4×16 → 8×16 | 160 |

每种方案含最多一次依赖前置结果的工具回填。缓存默认约 12,000 Token 前缀，四轮对照；完整矩阵另测约 24,000 Token 的四轮对照。规模由字符长度估计，实际计数与费用以上游 usage 和账单为准；预览也显示输出额度之和。Claude 原专项的缓存/压测参数独立生效，追加矩阵具有自己的阶段。

通用检测按四种协议映射同样的检测维度，变体数随协议适用性而变化；没有等价原生语义时明确标注不适用，不删除字段后算作通过。KVV 原生继续运行固定版官方断言，追加矩阵通过同一渠道的 Chat 接口执行并独立留证。

## 避免误读分数

**已判定通过率 = 通过 ÷（通过 + 失败）。** 模块与维度只对已得到结论的适用项计算；唯一综合分按已具备计分证据的模块权重汇总，维度分不再另算总分。对照、汇总、身份来源观察不重复计分。

**可判定率**说明适用项中有多少得到通过或失败结论。证据不足不会得到 40 分或被算作通过；全部未知时得分为「—」。取消、前置失败、未覆盖及不适用均会说明原因。来源/身份观察单独列证据，不混入能力分数。

| 观测 | 通过率 | 可判定率 | 能说明什么 |
| --- | ---: | ---: | --- |
| 1 通过、1 证据不足 | 100% | 50% | 已判定部分通过，另半部分仍需补测 |
| 1 通过、1 失败 | 50% | 100% | 两项均有结论，一项不符合约定 |
| 2 证据不足 | — | 0% | 无法形成能力得分，先解决缺失证据 |

原始 HTTP、鉴权、超时、限流与明确不支持分别记录。失败描述的是本次验收要求未满足；报告不会把所有 HTTP 错误归结为模型能力差。每条检查可追溯到实际请求 ID，批量模型之间不共用证据。

## 结论、缓存率与耗时

报告顺序为结论与耗时、模块总览、能力评分、方法及证据，完整测试清单放在末尾。输出上限只有实际超限证据才概括为「观察到输出超限」；非法上限拒绝失败另作解释。合成注入失败表示指令隔离风险，不能证明上游插入提示词。

暖请求 Token 复用率按有效暖请求的缓存读取总量除以总输入量计算，排除冷请求和改前缀对照。OpenAI 总输入已包含缓存；Anthropic 原始总输入为普通输入、缓存读取、缓存创建之和；已归一化的总输入不再重复相加。报告注明有效暖请求数量，缺字段不按零处理，也不以此认证实际账单。

总耗时使用真实起止区间或保存的实际运行耗时，不累加并发请求时长。请求 P50/P95 包含有有效耗时的成功和失败样本，阶段耗时保留各并发档位实际经过时间。只有请求起止时间时标明「请求观测窗口」，旧记录缺失的全程或阶段耗时显示「未记录」。

## 服务端 API

登录会话与 CSRF Token 仍然必需。`POST /api/acceptance/plan` 预览追加矩阵，`POST /api/claude/plan` 预览 Claude 原专项与追加矩阵；均不需要渠道密钥。`POST /api/runs` 执行时提交相同的选择及密钥。

新增字段：`matrix_profile` 为 `quick`、`standard`、`comprehensive` 或 `off`；`matrix_modules` 是 `protocol`、`tools`、`multimodal`、`max_tokens`、`injection`、`cache`、`stress` 的选择数组。新网页显式发送 `standard`。旧 API 调用未传方案时保持 `off`，避免升级后悄然增加既有自动化的模型用量。

JSON 结果保留 `native_summary` 与 `matrix_validation`，后者包含逐项 `cases`、逐请求 `samples`、摘要与指标。HTML 统一汇总，但仍区分原专项与新增证据。历史报告重新下载可更新展示方式，不会补造当时没有执行的测试。
